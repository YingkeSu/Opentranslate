# SOP：浏览器 LLM 翻译插件开发与发布流程

## 1. 目的

确保团队在“速度优先 + 流式优先”目标下，稳定推进开发、测试、发布与故障处理。

## 2. 角色与职责

- PM：范围与优先级管理，验收标准定义
- FE/Extension：功能实现、性能优化、跨浏览器兼容
- QA：测试设计、回归执行、门禁验证
- Maintainer：发布与回滚管理

## 3. 开发 SOP

## 3.1 需求冻结

- 每个 Sprint 明确：必做、可选、不做
- 必须绑定量化指标（至少含 TTFT）

## 3.2 任务拆解与排期

- 每个任务必须有：输入、输出、DoD、风险
- 单任务建议 <= 2 人日，超出需再拆分

## 3.3 分支与提交规范

- 分支：`feat/<epic>-<topic>`、`fix/<topic>`
- 提交：`feat|fix|perf(scope): message`
- PR：描述必须包含“性能影响”与“回滚方式”

## 3.4 编码流程

1. 先定义接口与事件协议
2. 再实现 provider adapter
3. 接入路由、缓存、重试
4. 最后做 UI 优化和埋点

## 3.5 代码评审门禁

- 必须有 requestId 全链路
- 禁止在 content-script 中读取明文 API key
- 必须处理取消逻辑与超时逻辑

## 4. 测试 SOP

## 4.1 测试层级

- 单元测试：路由、缓存键、重试、错误码映射
- 集成测试：content-script <-> worker <-> adapter
- 端到端手测：真实网页划词流式翻译

## 4.2 测试场景

- 短文本、长文本、超长文本
- 弱网、丢包、429、500
- 用户中途取消
- 多 tab 并发

## 4.3 性能门禁

- 每次发布候选版本必须提交 TTFT 报告
- P50/P95 与上版本对比，不得显著退化
- 缓存命中与未命中需分别验证

## 5. 安全 SOP

- 权限最小化审查
- 密钥存储与访问路径审查
- 输入输出脱敏审查
- CSP 与消息 schema 校验检查

## 6. 发布 SOP

1. 冻结发布分支
2. 执行完整回归 + 性能门禁
3. 更新版本号与变更日志
4. 准备商店描述与隐私政策
5. 发布后 24h 监控关键指标

## 7. 故障响应 SOP

## 7.1 触发条件

- 错误率突增
- TTFT 明显上升
- fallback 失效率异常

## 7.2 快速处置

1. 降级高耗模型
2. 切换主 Provider
3. 临时关闭非核心特性（如二次润色）

## 7.3 复盘模板

- 现象
- 根因
- 影响范围
- 修复动作
- 预防措施
